# The 2026-10-11 handoff: the last MCP pass before sharing

> What `HANDOFF.md` (7013edb) asked for, what two independent reviews found, what was decided,
> and what shipped. The numbers are the gate's; the next release ratchets against them. Written by
> the orchestrating session on 2026-10-11; the maintainer cuts the release.

## Why a pass, and why the last one

`fvtt-mcp-dnd5e` is about to be run by people other than its maintainer. The handoff written
after the 2026-10-10 overnight run listed six items (bridge-status #9, a readonly preset #8,
receipts and undo on every write #6, the run-script follow-up #13, journal statblocks #11,
init #7). The brief for this pass: solid and serverable, perf-aware, best-practice architecture,
no bloat, lasting; every MCP issue closed at the end, with any real bug opened, fixed and closed.

Two review sessions read the handoff and the code independently. They agreed on more than they
disputed; the orchestrator synthesized their findings into one plan, put the three real
disagreements to the maintainer, and had each step executed by its own agent with a file-level
brief, reviewed every diff, and had the reviewers read the two commits that carried the most risk.

## What the reviews found before a line was written

- The handoff's `bridge-status` tool would have broken both context ceilings (tools/list had 266
  chars of headroom; the always-on set 322). `get-world-info` already reported versions, host and
  role. **Fold, do not add.**
- The handoff's readonly rule ("a tool with an action is write") would have dropped every read
  inside the `manage-*` tools. **Tags per tool and per action.**
- The handoff's receipts design reused run-script's machinery as it was, and that machinery had
  three defects the reviews found independently: a follow-up `lastReceipt` read races (calls are
  not serialized), page-global hooks cross-attribute concurrent calls (undo A would revert B's
  work), and `toObject()` pre-images copy a whole scene per `activate-scene`. **One choke point
  under a write lock, pre-images per path from `_source`, the receipt beside the result.**
- Pre-images in a world journal (#13) would have doubled every write, broadcast MB-scale
  pre-images to every connected client, and left the user's data in their DB. **A Node-side file
  store instead; the world journal and the approval hash not planned.**
- Four bugs in the unreleased code: a dry run executed `remapSceneTeleporters` for real (the verb
  regex had no `remap`); `[].constructor.constructor('return this')()` left the facade while the
  text claimed "no way out by design", and the word check refused ordinary prose in strings; a
  synchronous loop in a script held the seat until `disconnect-bridge`; eviction trusted a bare
  pid. **Opened as #14–#17, fixed, closed.**

## The decisions the maintainer made (2026-10-11)

- **D1, the run-script sandbox.** Not a Web Worker rewrite, and `scripting` stays on by default:
  the join user's role is the enforceable boundary; the shadowing and the word check guard against
  accidents and say so.
- **D2, client-neutral (#5).** Closed as not planned for this line: the audience is Claude Code
  and the skills are half the product; the server is already neutral on the wire. `AGENTS.md`
  ships; `npm run init` prints the generic `mcpServers` block.
- **D3, statblocks (#11).** A skill note on the existing `html` block at 0 chars, the §2.1 trade
  stated, rather than a typed block at ~800 chars and a ceiling raise.
- **D4.** Commit per step, push once at the end.

## What was deliberately not built

- A Worker-based script runner (D1). A world-journal pre-image store and a dry-run approval hash
  (#13). Skills as MCP prompts, per-client config writers, a default-user rename, a Streamable
  HTTP transport (#5). A typed statblock block (#11). MCP tool annotations (`readOnlyHint`,
  ~2.8k chars; a ceiling decision for a later pass, noted in #8). The Linux GPU numbers (#10) wait
  for the Ubuntu box and live in suite issue #5.
